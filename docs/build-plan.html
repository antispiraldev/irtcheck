01What the spike found

The spec names two risky assumptions and asks that they be checked first. Both are now checked. One holds; one does not, and it takes the stack with it.

F·1

py-irt cannot be a runtime dependency

The maintained py-irt is real — nd-ball/py-irt, currently 0.7.1 — but every release from 0.4 onward declares Requires-Python >=3.9,<3.12. The spec targets 3.11+. The intersection is Python 3.11 exactly.

The failure mode is worse than a version error. On this machine (3.12.3), pip install py-irt resolves happily — to 0.1.1, an abandoned 2020 fork whose fit() assembles its summary list on the last line and then returns without it, and which imports pyro.contrib.autoguide and the pre-1.0 MCMC(...).run() API. It is 8.3 kB and it will not fit anything. Anyone on 3.12+ installing irtcheck gets that silently. Its pins are also our ceiling: typer<0.15 and rich<14, both of which the CLI wants.

Recommendation: write the 2PL directly in Pyro and keep py-irt as a cross-check fixture, never a dependency. The model and guide are ~90 lines, the SVI loop ~60. We need the variational posterior in hand anyway — the spec requires credible intervals on a_i, and py-irt's surface is oriented to point estimates. Dropping it restores 3.11+  … 3.13 and removes eleven transitive pins.

F·2

Per-item records do exist in the wild — adapters stay at step 7

Inspect writes them by default: EvalSample in src/inspect_ai/log/_log.py:419 carries id: int | str and scores: dict[str, Score] on every sample of every eval log. lm-eval-harness writes them too, but only under --log_samples alongside an --output_path; without those flags it keeps aggregates only.

The input contract survives unchanged and adapters do not need to move to step 1. The cost is one README line: lm-eval users with an existing run have to re-run it with --log_samples. That is a re-run of an eval we told them we would never make them run, so it belongs in the README prominently, not in a footnote.

F·3

The headline number has no data behind it yet

Synthetic matrices prove correctness — we generate from known a, b, θ and check recovery — but the leave-one-model-out rank correlation that the README is supposed to lead with needs a real suite scored per item by five or more models. We do not have one, and we are not allowed to produce one (no inference, by design).

Scheduled as a wave-2 spike, not assumed. If no public per-item matrix turns up, the fallback is to publish the validation curve on synthetic data with the generating parameters stated, and say plainly that it is synthetic. A stated synthetic number is credible; an unlabelled one is not.

02Three decisions, now made

Signed off 2026-09-03. Recorded here because each is something a wave-1 agent would otherwise have to re-derive, or get wrong.

D·1 — stack · decided

The Pyro model is ours. py-irt is not a dependency.

Written directly against Pyro, so the supported range is Python 3.11–3.13 rather than 3.11 alone, and typer/rich are not pinned by someone else's ceiling. py-irt survives as a wave-2 cross-check on a throwaway 3.11 venv, beside R's mirt — so the README can still say the estimates were validated against it.

Consequence CI runs a 3.11 / 3.12 / 3.13 matrix, and that matrix is what stops this quietly regressing.
D·2 — validation · decided

Score the held-out model both ways; headline plain accuracy.

Plain accuracy over the anchor items is what a user actually does once they have the set, so it is the number that has to hold up. θ re-estimated with item parameters held fixed is reported alongside it, because the two diverge when an anchor set skews hard or easy, and that divergence is itself worth seeing.

Owner agent B, wave1/select-validate.
D·3 — repo · decided

Default branch master; repo private.

github.com/antispiraldev/irtcheck, matching AudioBookLib. The guard protects master and main either way.

One schema change fell out of D·2

The spec writes the command as irtcheck validate suite.irt — one argument. But leave-one-model-out refits k times, so it needs the raw response matrix, not the posteriors. Rather than make the headline command depend on the user still having the original JSONL unchanged beside the artifact, the artifact carries its own responses: three small integers per response, and gzip flattens them. --no-embed-responses opts out, and validate then says exactly what is missing rather than failing obscurely.

Why four agents can share wave 1 without touching each other

Two decisions do the work, and they are the only reason this parallelises at all.

The fit artifact is the contract, and wave 0 can fabricate one. report, select, validate and the HTML output all consume an IrtFit; none of them needs a fitter to exist. Wave 0 ships synth.py, which emits a valid IrtFit with known ground-truth parameters without fitting anything. That module is not a testing convenience — it is what decouples agents B, C and E from agent A, who has the slowest and riskiest job.

Wave 0 pre-creates every file two agents would otherwise both edit. cli.py lands with all four commands already registered and stubbed to NotImplementedError, so each wave-1 agent edits only its own command module. pyproject.toml lands with the full dependency set for all four waves. Neither file is opened again in wave 1. This is the difference between "we agreed not to conflict" and "a conflict is not reachable".

What deliberately is not parallelised

  • Two agents must never both be inside fit/. A sign or scaling error in a Pyro guide hides well, and reviewing a merge of two people's variational approximations is worse than writing it once, carefully.
  • Wave 0 stays one agent. It could split into infra and contracts, but they meet in pyproject.toml and the whole thing is under an hour of work — the coordination costs more than it saves.
  • The wave-2 wiring commit lands before E, F and G merge, because it is the first moment the end-to-end path is real and it may move interfaces.

05The artifact schema

This is the interface four agents build against, so it is worth reading closely. Gzipped JSON, not a pickle or a torch checkpoint: it stays inspectable, diffable, and readable without importing torch.

{
  "schema_version": 1,
  "irtcheck_version": "0.1.0",
  "model": {"kind": "2pl", "priors": "hierarchical", "identification": "a > 0, theta ~ N(0,1)"},

  "respondents": {
    "key":     ["model_id", "prompt_variant"],   // --respondent-key
    "count":   12,
    "n_real":  5,                                // pseudo-respondents excluded
    "ids":     ["claude-sonnet-4-5|v1", ...],
    "derives_from": ["claude-sonnet-4-5", ...],  // load-bearing for holdout
    "theta":   {"mean": [...], "sd": [...], "hdi_low": [...], "hdi_high": [...]}
  },

  "items": {
    "count":   4312,
    "ids":     ["mmlu_hs_bio_0412", ...],
    "a":       {"mean": [...], "sd": [...], "hdi_low": [...], "hdi_high": [...]},
    "b":       {"mean": [...], "sd": [...], "hdi_low": [...], "hdi_high": [...]},
    "n_resp":  [...],
    "p_correct": [...],
    "flags":   [["insufficient-data"], [], ["ceiling"], ...]
  },

  "diagnostics": {"elbo_final": ..., "elbo_history": [...], "epochs": ..., "seed": ...},
  "passthrough": {"subject": {...}, "split": {...}},

  // The matrix the fit came from, so `validate` refits with one argument.
  // Sparse triplets; omitted entirely under --no-embed-responses.
  "responses": {"rows": [...], "cols": [...], "obs": [...]}
}

Two flags that are easy to conflate and must not be: dead means the item confidently does not discriminate — the upper end of its a interval is below threshold. insufficient-data means we cannot tell, because the interval spans zero. The first is a finding about the suite. The second is a finding about the data you gave us, and it excludes the item from ranking and selection rather than ranking it anyway.

The carve-out the guard needed

The guard denied wave 0's own first commit, and by its own rules it was right to — which is how it surfaced a real gap rather than an inconvenience. Adding a linked worktree refuses to run against an unborn HEAD, so the remedy rule 1 points at (“work in .claude/worktrees/<name>”) does not exist yet, and a repo with no history has nothing for another agent to be racing over. has_commits() permits the bootstrap commit and nothing else — it can be true at most once in a repository's life. The guard's own tests assert that the very next commit in that same tree is denied again, and that pushing to master is denied even during the bootstrap. 59 tests now, up from the 55 inherited.

What the contracts job actually asserts

  • SCHEMA_VERSION appears exactly once, and an artifact written by the current code round-trips byte-identically through save/load.
  • Every command registered on the CLI answers --help, and no two commands declare the same flag with different meanings.
  • pip install -e . resolves on 3.11, 3.12 and 3.13 — the check that would have caught F·1 on day one.

Testing a stochastic fit without flaky CI

SVI is stochastic, and a flaky test across four concurrent agents costs more than it catches. Every fit test seeds pyro.set_rng_seed, runs on CPU, and asserts recovery of synthetic ground truth within a stated tolerance rather than exact values. The fit tests carry a slow marker and run in their own CI job, so the other three agents get a fast lane that does not install torch.

07Still open

  • Minimum viable respondent count. The spec is right that this should come from synthetic data rather than a guess. It is a wave-3 study: sweep N from 3 to 40, find where the a intervals stop spanning zero for most items. Until then the tool flags per-item and does not refuse wholesale.
  • Thresholding a continuous raw_score. Deferred past v1. If it lands, the threshold prints in the report header — a binarisation the reader cannot see is a silent change to what the model means.
  • A real response matrix (F·3), assigned to agent G as a spike with a stated fallback.
